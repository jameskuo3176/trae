# Final Django/Mongo/Vue migration runbook

This is the operational source of truth for the current Django migration.
`MIGRATION_V4.md` is retained only as historical context.

## Canonical modules and versions

`GlobalModule` stores one canonical module name in the default relational
database. Names are Unicode NFKC-normalized, trimmed, case-folded for identity,
must not be blank, and are globally unique by `normalized_name`.
`ProjectModule` is the explicit many-to-many project association. A module may
belong to multiple projects; a project may contain multiple modules.
`LegacyModuleMapping` preserves each `(project_id, legacy_module_id)` mapping so
project-local records remain reversible and API v2 can expose global IDs.

New imports derive `version` only from `full_dir`:

1. Normalize slash direction, repeated separators, and `.` segments.
2. Reject blank paths and any `..` traversal.
3. If a `main` segment has a directly preceding valid `regr_*` segment, use it.
4. Otherwise use the last valid `regr_*` segment.
5. If none exists, reject the import with `version_not_in_path`; there is no
  payload/version fallback.

Examples: `/runs/regr_42/main/cpu` and
`D:\runs\regr_old\x\regr_42\main\cpu` both derive `regr_42`.

## Target architecture

- PostgreSQL is Django's only default ORM database. It stores auth, API keys,
projects, canonical modules, permissions, review/configuration metadata and
other relational state.
- MongoDB stores QoR records, raw reports, violation paths, and run notes.
- `data/qor_recorder.db`, `qor_p_*.db`, and `*_syn_qor.db` are migration inputs
only. `PERSISTENCE_MODE=mongo` does not create or open project SQLite files.
- `DB_TYPE=sqlite`, `PERSISTENCE_MODE=orm`, and `hybrid` are explicit
compatibility/rollback choices, not steady-state defaults.



## Preflight and coordinated backup

1. Stop uploads and other writers.
2. Record image/code versions and copy `.env` securely.
3. Back up every SQLite file with writers stopped; record SHA-256 hashes and run
  `PRAGMA integrity_check`.
4. Back up the target stores independently:

```bash
mongodump --uri "$MONGODB_URI" --db "$MONGODB_DB" \
  --archive="qor-mongo-$(date +%Y%m%d-%H%M%S).archive.gz" --gzip
pg_dump "$DATABASE_URL" --format=custom \
  --file="qor-postgres-$(date +%Y%m%d-%H%M%S).dump"
python manage.py check --deploy
python manage.py showmigrations
```

For file-backed SQLite, copy `data/` only while writers are stopped (or use the
SQLite backup API). Keep the relational and Mongo backups under one timestamp.
Verify archive readability and restore a sample in a non-production namespace.

## Migration order

All custom copy commands are dry-run by default. Use a newly created PostgreSQL
database: the metadata command deliberately refuses to merge into non-empty
business tables. Django `migrate` creates schemas only and does not copy data.

```bash
export DB_TYPE=sql
export DATABASE_URL='postgresql://...'
export PERSISTENCE_MODE=mongo

# 1. Create PostgreSQL schema.
python manage.py migrate --noinput

# 2. Main SQLite -> PostgreSQL. Includes users, password hashes, API keys,
# projects, memberships and all other tables present in the legacy main DB.
# contenttypes/permissions are regenerated by migrate and referenced by
# natural keys; sessions are intentionally not copied.
python manage.py migrate_sqlite_metadata_to_postgres \
  --source data/qor_recorder.db
python manage.py migrate_sqlite_metadata_to_postgres \
  --source data/qor_recorder.db --execute \
  --fixture-out backups/metadata-migration-audit.json

# 3. Validate/reconcile legacy project schemas after their verified backup.
python manage.py migrate_project_databases --check
python manage.py migrate_project_databases

# 4. Project SQLite relational state -> PostgreSQL. This copies modules,
# reviews, annotations, images, snapshots and light QorRecord FK anchors.
# It omits record metrics/raw reports/violations/notes. The target project
# tables must be empty; the command intentionally refuses merge/re-run.
python manage.py migrate_project_metadata_to_postgres
python manage.py migrate_project_metadata_to_postgres --execute

# 5. Project-local modules -> canonical PostgreSQL module mappings.
python manage.py migrate_global_modules
python manage.py migrate_global_modules --execute

# 6. Project SQLite heavy rows -> MongoDB.
python manage.py migrate_sqlite_to_mongo
python manage.py migrate_sqlite_to_mongo --execute
```

Use `--project-id ID` to canary the module/heavy-data steps. The project
metadata command is a one-shot all-project copy into empty destination tables;
it refuses reruns rather than risking cross-project primary-key duplication.
The Mongo command
upserts by `(project_id, legacy_id)`, so reruns are idempotent, creates indexes,
reports source/destination counts (including raw reports), and exits non-zero
on missing files, missing module mappings, write errors, or count shortfalls.
Re-run dry-runs after execution and retain the SQLite files unchanged.

Persistence modes:

- `mongo` (**Compose / recommended default**): API v2 reads Mongo; project
SQLite routing and creation are disabled. Relational review/module state is
stored in PostgreSQL.
- `orm`: relational/project database reads and writes only (no Mongo).
- `hybrid` (**cutover only**): relational import plus best-effort Mongo mirror;
reads prefer Mongo and fall back to ORM. Do not keep as a long-term default.

Reviews, users, projects, module metadata, and dashboard configuration remain
relational in every mode. Django never uses Mongo as a full ORM primary DB.

## Vue cutover

1. Build from repository root context because `frontend-vue/` is a sibling of
  `QoR_Recorder/`.
2. Run lint, type-check, Vitest, production build, and Playwright.
3. Deploy Django/Mongo first and verify `/health/live`, `/health/ready`, and API
  v2 through Nginx.
4. Deploy the Nginx image containing `frontend-vue/dist`.
5. Verify authenticated dashboard data, saved configuration API, Picker
  Apply/Cancel, CSRF-protected writes, and lazy raw reports.
6. Keep `/legacy/dashboard/` available during the acceptance window.

```bash
docker compose build
docker compose up -d
docker compose exec django python manage.py check --deploy
curl -fsS http://localhost/health/live
curl -fsS http://localhost/health/ready
```



## Rollback and restore

Application rollback: stop writers, restore the previous image tags and the
coordinated PostgreSQL/Mongo backups. A temporary `PERSISTENCE_MODE=orm`
rollback may read retained project SQLite, but only with code/schema versions
that support it. Do not delete SQLite or Mongo data merely to roll back reads.

Data rollback: stop all writers, restore the coordinated relational snapshot,
then restore Mongo into an empty database or use `--drop` only after confirming
the target:

```bash
mongorestore --uri "$MONGODB_URI" --db "$MONGODB_DB" \
  --archive=qor-mongo-TIMESTAMP.archive.gz --gzip --drop
```

Restore uploads with the matching snapshot. Run migrations/checks, compare
counts, and smoke-test both UIs before reopening writes. Never use
`docker compose down -v` as a rollback or backup operation.

  ```

  ```
